# تحقیق: اکوسیستم و محدودیت‌های بومی ایران

> ⚠️ **بازنگری 2026-09-23:** برخی پیامدهای فنی این سند (Outbox، Ledger، `NationalCode` و رمزنگاری بالینی) در ADR-016 ساده یا به بعد از 1.0 موکول شدند. **منبع تصمیم نهایی `docs/03-architecture/` است.** این سند فقط یافته‌های تحقیق را نگه می‌دارد.

> این نکات مستقیماً روی معماری اثر دارند. هر مورد با «← پیامد» به تصمیم فنی متصل شده است.

## 1. تقویم و زمان

- **تقویم جلالی (شمسی)** برای همه نمایش‌ها؛ ذخیره همیشه میلادی/UTC.
  ← پیامد: `DATETIME` به UTC در دیتابیس؛ تبدیل فقط در لایه Presentation.
- **ایران از 1402 (2023) ساعت تابستانی را لغو کرده است.** tzdata از نسخه 2022b این را منعکس می‌کند. سرورهای با tzdata قدیمی ممکن است هنوز 1 ساعت جابجا کنند.
  ← پیامد: از `Asia/Tehran` از طریق IANA استفاده شود، ولی در Site Health یک **چک سلامت tzdata** بگذاریم (مقایسه offset تیر ماه با +03:30) و هشدار دهیم.
- PHP `ext-intl` از `IntlDateFormatter` با `fa_IR@calendar=persian` پشتیبانی می‌کند، اما روی همه هاست‌های اشتراکی ایرانی فعال نیست.
  ← پیامد: یک پیاده‌سازی **خالص PHP الگوریتم جلالی** (بدون وابستگی) + استفاده از intl در صورت وجود. هر دو با تست Property-based هم‌ارز شوند.
- مرورگرها `Intl.DateTimeFormat('fa-IR-u-ca-persian')` را پشتیبانی می‌کنند (فرمت‌کردن)، ولی محاسبات تقویمی (اول ماه، تعداد روز ماه) را نه.
  ← پیامد: در JS از کتابخانه کوچک `jalaali-js` (~2KB) برای محاسبات + `Intl` برای فرمت.
- **تعطیلات رسمی:** تعطیلات قمری (عاشورا، عید فطر و...) با رؤیت هلال تعیین می‌شوند و **قابل محاسبه قطعی نیستند**. تقویم رسمی هر سال توسط مرکز تقویم مؤسسه ژئوفیزیک اعلام می‌شود.
  ← پیامد: دیتاست تعطیلات به‌صورت **JSON نسخه‌دار سالانه** همراه افزونه + امکان به‌روزرسانی از راه دور (اختیاری) + ویرایش دستی توسط مدیر. هر «Holiday Calendar» یک موجودیت است که به منابع/مکان‌ها اختصاص می‌یابد.
- شروع هفته: **شنبه**. آخر هفته: جمعه (و برای برخی کسب‌وکارها پنجشنبه بعدازظهر).
  ← پیامد: `week_start` قابل‌تنظیم، پیش‌فرض شنبه.

## 2. پول و ارز

- واحد رسمی **ریال (IRR)**، واحد رایج گفتاری **تومان** (= 10 ریال). درگاه‌ها گاهی ریال و گاهی تومان می‌گیرند (زرین‌پال پارامتر currency دارد؛ زیبال ریال).
  ← پیامد: **پول همیشه به‌صورت عدد صحیح در کوچک‌ترین واحد (ریال) با `BIGINT`** ذخیره شود + کد ارز. هر Gateway Adapter مسئول تبدیل به واحد مورد انتظار خود است. هرگز float.
- لایحه حذف چهار صفر (واحد جدید «تومان» = 10,000 ریال) در جریان است.
  ← پیامد: نمایش پول از طریق یک `MoneyFormatter` قابل‌پیکربندی (ریال / تومان / تومان جدید)، نه hard-code.
- اعداد فارسی (۰-۹) و عربی (٠-٩) در ورودی کاربر.
  ← پیامد: `DigitNormalizer` در لایه ورودی (قبل از Validation) برای همه فیلدهای عددی، موبایل، کد ملی، کد تخفیف.

## 3. هویت و داده‌های شخصی

- **موبایل** شناسه اصلی کاربر ایرانی است (نه ایمیل). فرمت‌ها: `09xx`، `9xx`، `+989xx`، `00989xx`، با ارقام فارسی.
  ← پیامد: `PhoneNumber` Value Object با نرمال‌سازی به E.164 (`+989123456789`)؛ ایمیل اختیاری. ورود با **OTP پیامکی**.
- **کد ملی** با الگوریتم چک‌سام 10 رقمی قابل اعتبارسنجی است. **کد اتباع** (فراگیر) برای بیماران غیرایرانی.
  ← پیامد: `NationalCode` Value Object + گزینه «اتباع خارجی».
- نرمال‌سازی متن فارسی: `ي`→`ی`، `ك`→`ک`، نیم‌فاصله (ZWNJ)، حذف اعراب برای جستجو.
  ← پیامد: `PersianTextNormalizer` برای ستون‌های جستجو (`search_name` نرمال‌شده جدا ذخیره شود).
- قانون جامع حمایت از داده‌های شخصی در ایران هنوز کامل اجرایی نشده، اما **رازداری پزشکی** الزام اخلاقی و قانونی است.
  ← پیامد: رمزنگاری فیلدهای حساس بالینی در سطح اپلیکیشن (libsodium)، Audit Log دسترسی به پرونده، حداقل‌سازی داده، امکان خروجی/حذف داده بیمار.

## 4. پیامک

- پیامک‌های خدماتی (OTP، یادآوری) در ایران باید با **پترن (قالب تأییدشده)** و از **خط خدماتی** ارسال شوند؛ پیامک متنی آزاد از خط تبلیغاتی به شماره‌های «لیست سیاه مخابرات» نمی‌رسد.
  ← پیامد: مدل اعلان باید **Template-first** باشد: هر اعلان = یک کلید رویداد + نگاشت متغیرها به پترن هر Provider. متن آزاد فقط Fallback.
- Providerهای رایج (همه در یک Adapter Interface):
  | Provider | نکته |
  |---|---|
  | کاوه‌نگار (Kavenegar) | `verify/lookup` با template و token1..3 (+ token10, token20 با فاصله) |
  | IPPanel / فراز اس‌ام‌اس | Pattern API (کد پترن + متغیرهای نام‌دار) |
  | SMS.ir | Verify API (templateId + parameters) |
  | ملی پیامک (Melipayamak) | SendByBaseNumber (BodyId + متغیرها با `;`) |
  | پارس‌گرین، قاصدک، آسانک، پیامک پنل، آسیاتک | افزودن در فاز بعد با همان Interface |
  ← پیامد: `SmsProvider` Port + Adapterها + **Failover** (اگر Provider اصلی خطا داد، دومی) + Outbox با Retry + ثبت هزینه/وضعیت تحویل.

## 5. پرداخت

- درگاه‌های واسط (PSP) رایج: **زرین‌پال (v4)**، **زیبال**، پی‌پینگ، نکست‌پی، وندار، جیبیت، پی‌استار، سپال، شپا، ایران‌درگاه، بیت‌پی. آیدی‌پی: وضعیت فعلی باید پیش از پیاده‌سازی بررسی شود.
- درگاه‌های مستقیم بانکی (شاپرکی): ملت (به‌پرداخت)، سامان (سپ)، سداد (ملی)، پارسیان، پاسارگاد، ایران‌کیش، اقتصاد نوین، صادرات.
- **خرید اقساطی (BNPL):** اسنپ‌پی، دیجی‌پی، ازکی وام — کاربران ایرانی استقبال زیادی دارند.
- شاپرک ممکن است ناگهانی درگاه‌ها را قطع کند (سابقه قطع 400 هزار درگاه در 1400 به‌دلیل پرونده مالیاتی).
  ← پیامد: `PaymentGateway` Port با جریان استاندارد `initiate → redirect → callback → verify → (inquiry)`؛ **Failover بین درگاه‌ها**؛ الگوی **Idempotency** روی verify (callback ممکن است دوبار بیاید)؛ Job تطبیق (Reconciliation) برای تراکنش‌های بلاتکلیف با API `inquiry` / `unVerified`.
- زرین‌پال v4: `pg/v4/payment/request.json` → `StartPay/{authority}` → `pg/v4/payment/verify.json`؛ همچنین `inquiry.json` و `unVerified.json`.
- افزونه Gateland نمونه خوبی از **لایه انتزاعی درگاه + Failover** است (46 درگاه).
  ← پیامد: امکان استفاده از Gateland به‌عنوان یک «Payment Channel» اختیاری، علاوه بر Adapterهای بومی خودمان.
- ووکامرس: بسیاری از سایت‌ها درگاهشان را در ووکامرس تنظیم کرده‌اند.
  ← پیامد: `WooCommerceChannel` اختیاری؛ **Ledger ما منبع حقیقت است** و وضعیت سفارش ووکامرس با Webhook داخلی به آن همگام می‌شود (نه برعکس).

## 6. محدودیت‌های زیرساخت و تحریم

- **سرویس‌های گوگل**: Google Cloud Console برای IP ایرانی مسدود است؛ سرورهای داخل ایران ممکن است به `googleapis.com` دسترسی نداشته باشند. reCAPTCHA و Google Fonts ممکن است بارگذاری نشوند.
  ← پیامد: Google Calendar **اختیاری** و با Circuit Breaker؛ کپچا داخلی (تصویری/ریاضی سبک) + Adapter برای **آرکپچا (ArCaptcha)** ایرانی؛ **فونت وزیرمتن (Vazirmatn، OFL) به‌صورت محلی** bundle شود؛ هیچ asset از CDN خارجی در Runtime.
- **Zoom تحریم است.** جایگزین‌ها: **اسکای‌روم (Skyroom)**، Jitsi (self-hosted)، BigBlueButton، Google Meet (با محدودیت)، **تماس تلفنی** (رایج‌ترین مشاوره در ایران).
  ← پیامد: `MeetingProvider` Port؛ «نوع ویزیت» (حضوری، تلفنی، ویدیویی، متنی) مفهوم درجه‌یک در Service.
- پیام‌رسان‌ها: تلگرام/واتس‌اپ فیلترند (هرچند پرکاربرد)؛ **بله، ایتا، روبیکا** Bot API دارند.
  ← پیامد: `NotificationChannel` Port با Adapterهای SMS، Email، Web Push، Bale، Eitaa، Telegram.
- **قطعی/اختلال اینترنت بین‌الملل** به‌صورت دوره‌ای رخ می‌دهد؛ سرویس‌های داخلی معمولاً کار می‌کنند.
  ← پیامد: همه فراخوانی‌های خارجی با Timeout کوتاه، Retry با Backoff، Circuit Breaker، و **هیچ فراخوانی خارجی در مسیر بحرانی رزرو** (غیر از درگاه پرداخت).
- **هاست‌های اشتراکی ایرانی**: cPanel/DirectAdmin، معمولاً بدون Redis/Memcached، محدودیت `max_execution_time`، WP-Cron وابسته به بازدید، گاهی بدون `ext-intl`/`ext-sodium`.
  ← پیامد: هیچ وابستگی به Redis؛ Action Scheduler برای صف؛ راهنمای Cron واقعی در Site Health؛ Polyfill برای sodium (`sodium_compat` داخل WP Core موجود است)؛ کارهای سنگین Batch‌شده.

## 7. اعتماد و قانون کسب‌وکار

- **نماد اعتماد الکترونیکی (اینماد)** برای دریافت درگاه لازم است — خارج از دامنه افزونه، ولی در Onboarding راهنما بدهیم.
- **نسخه الکترونیک** (تأمین اجتماعی، بیمه سلامت، نیروهای مسلح) و **سپاس** API دارند ولی نیازمند مجوز/قرارداد هستند.
  ← پیامد: `InsuranceProvider` / `EPrescriptionProvider` Port تعریف شود ولی پیاده‌سازی در فاز آینده.
- فاکتور رسمی و **سامانه مودیان** (صورتحساب الکترونیکی مالیاتی) برای کسب‌وکارهای مشمول.
  ← پیامد: مدل Invoice سازگار با فیلدهای سامانه مودیان طراحی شود (شناسه کالا/خدمت، ...) — Adapter در فاز آینده.

## 8. زبان و RTL

- رابط کاملاً RTL با **CSS Logical Properties** (`margin-inline-start` به‌جای `margin-left`) تا نسخه LTR (انگلیسی/عربی/ترکی) رایگان به‌دست آید.
- i18n استاندارد وردپرس (`__()`, `_n()`, `wp_set_script_translations`)؛ زبان مبدأ رشته‌ها **انگلیسی**، ترجمه فارسی کامل همراه افزونه — تا بازار بین‌الملل هم ممکن باشد.
- ارقام نمایشی فارسی به‌صورت تنظیم (پیش‌فرض فارسی در `fa_IR`).
