# روش کار با Agent (Claude Code)

> هدف: هر سشن، حتی بدون حافظه قبلی، **دقیقاً از جایی که کار مانده ادامه دهد**، کیفیت ثابت بماند و هیچ کاری ثبت‌نشده نماند.
> Skillهای پروژه: `/resume` (شروع سشن)، `/next-task` (اجرای یک Task)، `/wrap` (پایان سشن). این‌ها در `.claude/skills/` هستند.
> Subagent پروژه: `reviewer` (بازبینی قبل از commit)، در `.claude/agents/`.
> Skillهای WordPress، TDD و debugging و قانون اولویت آن‌ها: [05-agent-tooling.md](05-agent-tooling.md). محیط: [../04-engineering/02-dev-environment.md](../04-engineering/02-dev-environment.md). تله‌های فنی: [../04-engineering/03-implementation-notes.md](../04-engineering/03-implementation-notes.md).

## 1. شروع سشن (`/resume`)
1. `CLAUDE.md` خودکار بارگذاری می‌شود.
2. [02-progress.md](02-progress.md) را بخوان، به‌خصوص بخش «از اینجا ادامه بده».
3. 3 ورودی آخر [04-worklog.md](04-worklog.md) را بخوان.
4. `git status` و `git log --oneline -10` را بررسی کن. اگر تغییر commit‌نشده‌ای هست، اول بفهم مال کدام Task است.
5. **فقط** اسناد مربوط به Task بعدی را بخوان (مثلاً برای T1.4 فقط `03-booking-engine.md §2`). نیازی به خواندن همه docs نیست.
6. در یک پیام کوتاه به کاربر بگو: کجا هستیم و الان چه کاری انجام می‌شود.

## 2. اجرای یک Task (`/next-task`)
1. **علامت‌گذاری:** وضعیت Task را در progress به 🟨 تغییر بده.
2. **فهم:** معیار «انجام‌شده» در roadmap و اسناد طراحی مرتبط را بخوان. اگر ابهامی هست که **واقعاً** تصمیم کاربر است (نه چیزی که از اسناد یا عرف فهمیده می‌شود)، بپرس. وگرنه پیش‌فرض معقول را انتخاب کن و در Worklog ثبت کن.
3. **برنامه کوچک:** برای Taskهای بزرگ‌تر از حدود 5 فایل، اول یک برنامه چندمرحله‌ای بنویس (TodoWrite یا Plan mode).
4. **تست اول (TDD)** برای Domain و Application: اول تست شکست‌خورنده، بعد پیاده‌سازی.
5. **پیاده‌سازی** طبق [../04-engineering/01-principles.md](../04-engineering/01-principles.md)، به‌خصوص §0 (ضد Overengineering).
6. **تأیید واقعی:** دستورها را اجرا کن و خروجی را ببین: `composer lint`، `composer stan`، `composer test` و تست‌های JS و E2E مرتبط. **هرگز بدون اجرا ادعای «کار می‌کند» نکن.** اگر ابزاری در دسترس نیست (مثلاً Docker)، صریحاً بگو چه چیزی تأیید نشد.
7. **بازبینی:** Subagent `reviewer` را روی diff اجرا کن و یافته‌های معتبرش را اصلاح کن.
8. **مستندسازی:** Tracker (✅ + hash commit)، Worklog، و در صورت نیاز ADR جدید، CHANGELOG و README ماژول.
9. **Commit:** یک commit برای هر Task، با Conventional Commits، مثلاً `feat(scheduling): availability calculator (T1.4)`.
   - در صورت تغییر قابل توجه، commit میانی مجاز است.
   - **Push:** Remote `origin` (GitHub) وصل است. Push روی `main` در پایان هر `/wrap` انجام می‌شود، یا هر وقت کاربر بخواهد. `force-push` و بازنویسی تاریخچه **هرگز** بدون درخواست صریح کاربر انجام نمی‌شود.

## 3. پایان سشن (`/wrap`)
1. اگر Task نیمه‌کاره است، وضعیت 🟨 می‌ماند. در ستون یادداشت بنویس دقیقاً کجا ماند و قدم بعدی چیست.
2. بخش «از اینجا ادامه بده» در progress را به‌روز کن.
3. یک ورودی Worklog بنویس (قالب در [04-worklog.md](04-worklog.md)).
4. کارهای انجام‌شده را commit و روی `origin/main` push کن. کار نیمه‌کاره‌ای که تست‌ها را می‌شکند با پیشوند `wip:` روی شاخه جدا commit و push می‌شود. `main` همیشه باید سبز بماند.
5. خلاصه کوتاه به کاربر: چه شد، چه ماند، و تصمیمی که از کاربر لازم است.

## 4. قوانین کلی Agent
| قانون | توضیح |
|---|---|
| **منبع حقیقت = فایل‌ها** | حافظه سشن موقت است. هر چیز مهم در docs، progress یا worklog نوشته می‌شود |
| **تصمیم‌ها را دوباره باز نکن** | ADRهای `Accepted` قطعی‌اند. اگر مشکلی دیدی، ADR جدید پیشنهاد بده و کار را متوقف نکن |
| **گام‌های کوچک** | یک Task در هر زمان. PR و commit کوچک. تست بعد از هر تغییر معنادار |
| **Context را سبک نگه دار** | فایل‌ها را بخش به بخش بخوان. برای جستجوی گسترده در کد از Subagent `Explore` استفاده کن تا خروجی حجیم وارد Context اصلی نشود |
| **Subagent فقط با دلیل** | موارد مجاز: `Explore` برای جستجوی گسترده، `reviewer` برای بازبینی مستقل، و کارهای **واقعاً مستقل** موازی (مثلاً دو Adapter پیامک) با `isolation: worktree`. برای کاری که خودت با چند Read انجام می‌دهی Subagent نساز |
| **گزارش صادقانه** | تست شکست خورد؟ با خروجی گزارش کن. مرحله‌ای رد شد؟ بگو. فرض کردی؟ بنویس |
| **اقدام برگشت‌ناپذیر** | حذف فایل‌های کاربر، `git push`، `reset --hard`، تغییر خارج از Repo: **اول بپرس** |
| **امنیت** | هیچ Secret (کلید درگاه یا پیامک) در Repo یا لاگ نمی‌رود. برای تست از Sandbox یا Mock استفاده کن |
| **وابستگی جدید** | فقط با ADR. اول بپرس «آیا با 50 خط کد خودمان حل می‌شود؟» |
| **زبان** | گفتگو و docs به فارسی (اصطلاح فنی انگلیسی). کد، کامنت، commit و identifierها به انگلیسی |
| **نام کاری** | هیچ لیترال `vaqtyar` یا `vqy` خارج از جاهای مجاز (ADR-000) |

## 5. ترتیب اولویت در تعارض
1. درستی (قفل رزرو، پول، امنیت، داده)
2. معیار «انجام‌شده» Task
3. اصول مهندسی و ADRها
4. سرعت

## 6. وقتی گیر کردی
- دو تلاش ناموفق با یک رویکرد ← رویکرد را عوض کن یا مسئله را کوچک‌تر کن.
- سه تلاش ناموفق ← وضعیت ⛔ بگذار، علت و گزینه‌ها را در Worklog بنویس و از کاربر بپرس.
- محیط مشکل دارد (Docker، PHP یا Node نیست) ← دقیق گزارش کن و در صورت امکان بخش مستقل از محیط را جلو ببر.
